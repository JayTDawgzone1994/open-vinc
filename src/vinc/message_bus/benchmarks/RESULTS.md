# Windows x64 首次 Message Bus benchmark（2026-10-06）

## 環境與條件

- AMD Ryzen 7 5700X3D，8 cores／16 logical processors，約 32 GiB RAM。
- Windows 11 Pro 10.0.26200；MSVC 19.51.36257.0，CMake 4.3.2，Ninja，Release `/O2 /Ob2 /DNDEBUG`。
- 基底提交 `12cdbae` 加本次 benchmark。框架預設 pump idle 10ms，未改 timer resolution、優先權或 affinity。
- 一個中央、兩個獨立 ModuleHost；每組暖機至少 64 筆，正式 1,000 筆。16 組共 16,000 筆全數收到。
- 最終各組碰撞、覆蓋／未收到筆數、內容邊界檢查失敗均為 0。先前失敗試跑仍保留，不代表所有負載都無碰撞。
- 共享配置上限 4 GiB，正式最大配置為 3.9378 GiB（另有本機副本與程序資源）。
- 有節奏的延遲基準；表中 MiB/s 是實際負載的資料率，不是飽和吞吐量。不同組的負載頻率不完全相同。

## 觀察與限制

- 1～32 MiB 正式組使用 8 slots。64／128 MiB push 在較高頻率下讀者無法持續跟上；增加到預算內上限仍出現干擾，最後降頻才取得完整無碰撞結果。
- 校準及受干擾正式組共 8 組未達 clean 條件，均保留在 attempts 與原始紀錄。沒有用遺失後較小的樣本集宣稱成功。
- 最終組前後四分之一樣本的 P50 未呈現數百毫秒的累積；欄位保留於 CSV。這不是無限時間穩定性的證明。
- 小訊息送出呼叫遠短於整體延遲；預設 pump 等待與 Windows 排程是值得下一輪分離量測的因素。未以本次數字宣稱 memcpy 本身耗時十多 ms。
- 固定發布與 pump 週期的相位會影響分布，尤其 P50；不同時段的 P50 不能直接當作某路徑必然較快的證據。
- push 重用已配置的本機 payload；loan 每筆重新借用並初始化。完整路徑 P99 顯示初始化成本，不能只用 commit 的小耗時宣稱全程 zero-cost。
- P99 每組只有約 10 筆上端樣本；不是硬期限、最差情境或跨平台承諾。測試期間未關閉使用者其他應用。
- Linux／macOS 未實機測量；未執行飽和吞吐量測試。
